# hsbot 项目审计报告 · 2026-09-13

> 范围:hsbot/ 全部 11 模块 + scripts + tests(约 3100 行 + 测试)。
> 按"问题/冗余/流程结构/解耦/硬编码"五类分列,每条标注优先级(高/中/低)。

## 一、有问题的设计(bug 风险)

### 高
1. **快照持久化缺解析层结果**:`store.to_dict()` 不含 `pred_dmg/via/inferred`,
   `analysis.enrich` 只在渲染路径执行 → "显示的信息"与"保存的信息"不一致,
   训练/复盘拿不到伤害预估与归因。与"要保存这些信息"的诉求直接冲突。
   修法:enrich 后的富化字段并入 `to_dict`/快照 payload(渲染前同一份)。
2. **`Config` 可变默认值共享**:`DEFAULTS["overlay_colors"]` 是 dict,
   `Config.__init__` 浅拷贝 → 所有 Config 实例共享同一 color dict,
   任一实例原地修改会污染全局(潜伏 bug,当前未触发)。
   修法:`copy.deepcopy` 非标量默认值,或 DEFAULTS 只存不可变结构。
3. **`SessionStore` 并发竞争**:目录名 `strftime("%Y%m%d_%H%M%S")`,
   同秒双开两个 bot → 同目录同文件交错写。低概率高危害。
   修法:目录名加进程随机后缀,或启动时探测占用。

### 中
4. **`hero_power` 可能二次输出**:同实体先隐藏后揭示时
   (`card_id=None`→有名字)会连发 `英雄技能 → #126` 与 `英雄技能 → 月亮的祝福`
   两条;"渐进展示"还是"去重"语义未定义,建议去重并延迟到可知名。
5. **`analysis.enrich` 的 via 依赖 O(全实体) 扫描**:`enchantments_on` 每条
   费用事件全量扫实体;快照手牌再扫一遍(O(手牌×实体))。当前量级无碍,
   实体数上千时需索引(ATTACHED 反查表)。
6. **effects.json / overlay_state.json / 训练 jsonl 非原子写**:
   `write_text` 直接覆盖,中途崩溃产生截断文件。修法:临时文件+rename。
7. **跨午夜 Decks.log 归因**:corpus `_parse_log_time` 用 `datetime.now().date()`
   拼日期,`-43200` 秒补丁治标;跨午夜对局可能归因到错误卡组。
8. **live 导出训练样本无去重**:重复 attach 同一会话会重新导出(同路径覆盖,
   幂等但语义与 `_imported.json` 的"只导新"不一致)。

### 低
9. `store.unhandled` 上限 500 的裁剪是 O(n) `del [:n]`,可改 deque(maxlen)。
10. `_route` 在 enrich 之前维护 `summary`(使用未富化事件)——当前正确,
    但若富化改变 card_id(雷纳索尔推断),摘要与链路行会不一致。

## 二、冗余

### 高
1. **两套对局事实推导**:`corpus.export_game` 自行从 packet 树重新推导
   players/heroes/results/mulligan/turns,与 store 的衍生逻辑平行。
   每加一种新事实(今天的效果关联/宠物过滤)要同步两处,已经出现漂移:
   corpus 的宠物过滤是独立实现。修法方向:训练导出复用 store 的事件流/快照
   (结构化事件已是超集),corpus 只做落盘与归因。
2. **Decks.log 两套解析**:knowledge.parse_decks_log 与 corpus._deck_timeline
   各自解析同一文件(后者多取时间戳,前者取名),语义重复。

### 中
3. `snapshot_line` 与 `snapshot_block` 各自拼水晶/法强/牌库——派生字段
   两处维护,格式漂移风险;可由共同的"快照字段集"生成。
4. watcher._snapshot 每次重算 `game_meta(parser)`——一次会话内不变,可缓存。
5. render 内 `carddb.name` 同事件多次调用(26 处)——纯性能小事,可忽略。

### 低
6. tests 三个文件各自定义 `_store/_heroes` helper → 应上移 conftest。
7. `_REASON_CN`、`_KIND_COLORS`(已删)这类小表单处定义 ✓ 无重复。

## 三、流程处理结构

总体是健康的单向管线:
`Power.log 行 → feed(行级兜底) → hslog(包树) → cursor 逐包 → store.apply
→ 事件 → watcher._route(富化/渲染/落盘) → hub(console/overlay/file)`。

问题点(按数据流顺序):

1. **`_feed_many` 是隐式管线**:一个循环里依次做 行计数→尾包行形判定→真名
   采集→CREATE_GAME 边界(manager 重置/切片重置)→括号采集→喂 parser→
   抽牌行补事件。六种职责靠代码顺序耦合,无注释说明顺序依赖,新增行处理
   极易插错位置。建议:拆成有序的行处理器列表(每个处理器一个函数)。
2. **同一局边界三处逻辑**:`_feed_many`(CREATE_GAME 行:切片重置+manager
   重置)、`_detect_game`(flush 上一局+发终局+建新作用域)、`_new_game`
   (作用域替换+落盘+知识装载)。顺序敏感(切片收尾必须在作用域替换前),
   目前正确但脆弱,建议把"局边界协议"收敛到一个方法并写明不变式。
3. **异常隔离边界**:store 订阅者(事件回调)的异常不做隔离,靠
   `_process_tree` 外层 try;同批后续订阅者不再执行。建议 `_emit_event`
   内逐订阅者 try/except(日志即可),根治"一个回调炸掉整条链"。
4. **快照时机**:turn_start(对手回合开始)触发快照——语义合理,但
   `self.gs.meta = game_meta(parser)` 由外部注入 store 可变字段,
   破坏了"变更入口"封闭性(apply/note_friendly/hint_* 之外的第四入口)。
5. **同步单线程管线**:route→render→hub 全同步,快照重建(全量扫实体)会
   顶住轮询。当前量级无碍,标注为容量边界。
